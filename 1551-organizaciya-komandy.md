# Организация работы в команде разработчиков

**Проект: информационная система для управления заказами · МДК 02.02 · группа 3424А**

## 1. Цель работы

Изучить методы организации работы в команде разработчиков и применить их на практике: выбрать метод, описать его принципы, этапы, роли участников, разработать план работы команды на начальном этапе проекта и определить порядок коммуникации.

## 2. Обзор методов организации работы

| Метод | Суть | Когда подходит |
|---|---|---|
| Waterfall (каскад) | Этапы идут строго последовательно: анализ → проектирование → разработка → тестирование → внедрение | Требования полностью известны и не меняются |
| Agile | Семейство гибких подходов: итерации, частая поставка, реакция на изменения важнее плана | Требования уточняются по ходу проекта |
| Scrum | Agile-фреймворк: работа короткими спринтами (1–4 недели), каждый спринт даёт готовый инкремент продукта | Нужен регулярный результат и обратная связь заказчика |
| Kanban | Визуализация потока задач на доске, ограничение числа задач в работе (WIP-лимиты) | Непрерывный поток задач, поддержка, сопровождение |

## 3. Выбор метода

Для проекта выбран **Scrum**. Обоснование:

- требования к системе управления заказами будут уточняться по ходу работы (заказчик видит результат и корректирует пожелания) — Scrum допускает изменения между спринтами;
- команда небольшая (5 человек) — соответствует рекомендуемому размеру Scrum-команды;
- заказчику важно видеть прогресс: демонстрация работающего инкремента в конце каждого спринта;
- фиксированная длина спринта дисциплинирует команду и упрощает планирование сроков.

## 4. Принципы и этапы Scrum

**Основные принципы:**

- работа делится на спринты фиксированной длительности (в проекте — 2 недели);
- каждый спринт заканчивается работающей версией продукта (инкрементом);
- команда самоорганизуется: сама решает, кто и как выполняет задачи спринта;
- состав задач спринта не меняется после его старта.

**Этапы работы (цикл спринта):**

1. Планирование спринта — команда выбирает задачи из бэклога продукта в бэклог спринта.
2. Ежедневные стендапы — короткие встречи (15 минут): что сделано, что делаю, что мешает.
3. Разработка — выполнение задач спринта, код-ревью, тестирование.
4. Обзор спринта (демо) — показ инкремента заказчику, сбор обратной связи.
5. Ретроспектива — команда обсуждает процесс и решает, что улучшить в следующем спринте.

## 5. Роли и обязанности участников

| Роль | Обязанности |
|---|---|
| Product Owner (владелец продукта) | Ведёт бэклог продукта, расставляет приоритеты, принимает результат спринта (представитель заказчика) |
| Scrum Master | Следит за соблюдением процесса, устраняет препятствия, ведёт встречи |
| Ведущий разработчик | Общее руководство разработкой, архитектура системы, код-ревью |
| Программисты (2 чел.) | Разработка программного кода в соответствии с требованиями |
| Тестировщик | Проверка работоспособности кода, написание тестов, выявление ошибок |
| Аналитик | Анализ требований, разработка технических заданий, уточнение деталей у заказчика |

## 6. План работы команды на начальном этапе проекта

**Спринт 0 — подготовительная неделя (01.09–05.09):**

| № | Задача | Срок | Ответственный |
|---:|---|---|---|
| 1 | Сбор и анализ требований, формирование бэклога продукта | 01.09–03.09 | Аналитик, Product Owner |
| 2 | Настройка репозитория Git, таск-трекера и каналов связи | 02.09 | Scrum Master |
| 3 | Проектирование архитектуры и схемы базы данных заказов | 03.09–05.09 | Ведущий разработчик |
| 4 | Подготовка тестовой среды и плана тестирования | 04.09–05.09 | Тестировщик |

**Спринт 1 — первый инкремент (08.09–19.09):**

| № | Задача | Срок | Ответственный |
|---:|---|---|---|
| 1 | Модуль каталога товаров (добавление, список, остатки) | 08.09–12.09 | Программист 1 |
| 2 | Модуль оформления заказа со списанием со склада | 08.09–15.09 | Программист 2, ведущий разработчик |
| 3 | Модульные тесты для каталога и заказов | 12.09–17.09 | Тестировщик |
| 4 | Код-ревью и интеграция модулей | 16.09–18.09 | Ведущий разработчик |
| 5 | Демо инкремента заказчику, ретроспектива | 19.09 | Вся команда, Product Owner |

Контроль выполнения — на ежедневных стендапах и по состоянию задач на доске; задача считается выполненной, только если она протестирована и прошла код-ревью.

## 7. Коммуникация и обмен информацией

| Канал | Назначение | Регламент |
|---|---|---|
| Ежедневный стендап | Синхронизация работы, выявление препятствий | Каждый день, 15 минут, онлайн |
| Таск-трекер (доска задач) | Статусы задач: «запланировано» — «в работе» — «на проверке» — «готово» | Обновление ежедневно |
| Мессенджер (Telegram-чат) | Оперативные вопросы | В рабочее время, ответ в течение часа |
| GitHub | Код, код-ревью через pull request | Ветка на задачу, merge после ревью |
| Wiki-документация | Требования, ТЗ, решения по архитектуре | Обновление по мере изменений |

## 8. Вывод

Для проекта по созданию информационной системы управления заказами выбран метод Scrum: он обеспечивает регулярную поставку работающего результата и допускает уточнение требований между спринтами. Описаны принципы и этапы метода, распределены роли и обязанности шести участников, составлен детальный план начального этапа (подготовительная неделя и первый двухнедельный спринт) с задачами, сроками и ответственными, определены каналы коммуникации. Такая организация делает работу команды прозрачной: прогресс виден на доске задач ежедневно, а риски выявляются на стендапах до того, как сорвут сроки.
