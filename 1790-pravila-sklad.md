# Правила взаимодействия в команде разработчиков

**Проект: информационная система для управления складом · МДК 02.02 · группа 3424А**

## 1. Цель документа

Разработать правила взаимодействия в команде разработчиков, обеспечивающие эффективное сотрудничество при создании информационной системы управления складом: роли, коммуникация, решение конфликтов, управление изменениями, оценка эффективности, работа с документацией и контролем версий.

## 2. Роли и обязанности

| Роль | Функции и обязанности |
|---|---|
| Руководитель проекта | Планирование, контроль сроков и бюджета, связь с заказчиком, решение эскалаций |
| Аналитик | Требования, технические задания, уточнение деталей у складского персонала |
| Ведущий разработчик | Архитектура, код-ревью, технические стандарты проекта |
| Программисты | Разработка модулей по ТЗ, модульные тесты |
| Тестировщик | Тестовые сценарии, проверка, регистрация и верификация дефектов |

## 3. Правила коммуникации

- **Ежедневный стендап** — 15 минут: статус, планы, препятствия.
- **Еженедельная планёрка** — приоритеты недели, сверка с графиком.
- **Рабочий чат** — оперативные вопросы; ответ в течение часа в рабочее время.
- **Важные решения** — только письменно (задача в трекере или wiki): устная договорённость без записи не считается принятой.

## 4. Решение конфликтов и управление изменениями

- **Конфликт по техническому решению:** стороны письменно формулируют альтернативы с аргументами; решение принимает ведущий разработчик; спор по архитектуре эскалируется руководителю проекта.
- **Личный конфликт:** сначала прямой разговор, затем — через руководителя проекта как медиатора.
- **Управление изменениями:** любое изменение требований оформляется заявкой на изменение: что меняем, зачем, влияние на сроки; решение — руководитель проекта совместно с заказчиком; одобренные изменения попадают в бэклог и ТЗ обновляется.

## 5. Оценка эффективности команды

| Критерий | Для команды | Для участника |
|---|---|---|
| Сроки | Доля задач, закрытых в срок (цель ≥ 90 %) | Выполнение личных задач в срок |
| Качество | Число дефектов после релиза | Возвраты задач с ревью и тестирования |
| Процесс | Соблюдение Definition of Done | Обновление статусов на доске ежедневно |

Оценка проводится по итогам этапа; результаты обсуждаются на ретроспективе и используются для улучшения процесса, а не для наказаний.

## 6. Документация и контроль версий

- ТЗ, архитектурные решения и регламенты хранятся в wiki и актуализируются вместе с изменениями.
- Код — в Git: ветка на задачу, слияние в `main` только через pull request после код-ревью и зелёных тестов.
- Сообщения коммитов осмысленные: что и зачем изменено; код соответствует PEP 8.
- Релизы помечаются тегами версий (v1.0, v1.1).

## 7. Вывод

Разработанные правила покрывают полный цикл взаимодействия команды складского проекта: распределены роли, заданы регламенты коммуникации, определены процедуры решения конфликтов и управления изменениями, введены измеримые критерии эффективности и правила работы с документацией и версиями кода. Чёткие правила снижают неопределённость: каждый участник знает, кто за что отвечает, как сообщать о проблемах и как принимаются решения.
