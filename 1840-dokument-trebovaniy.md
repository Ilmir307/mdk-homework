# Документ требований к программному продукту «Система управления заказами»

**МДК 02.02 · группа 3424А**

## 1. Введение

Документ содержит требования к программному продукту «Система управления заказами интернет-магазина». Требования классифицированы по модели FURPS+ и проверены на соответствие стандартам ISO/IEC/IEEE 29148 (форма записи) и ГОСТ Р ИСО/МЭК 25010-2015 (полнота характеристик качества). Каждое требование однозначно, проверяемо и имеет идентификатор для трассировки.

## 2. Функциональные требования (F)

| № | Требование |
|---:|---|
| F1 | Система ведёт каталог товаров: название, цена, остаток на складе |
| F2 | Система регистрирует покупателей: ФИО, e-mail |
| F3 | При оформлении заказа система проверяет остаток и списывает товар со склада; при нехватке заказ отклоняется с сообщением |
| F4 | Система управляет статусами заказа по закрытому перечню: «новый», «оплачен», «отменён» |
| F5 | При отмене или удалении заказа товар возвращается на склад |
| F6 | Система формирует отчёт о продажах за период: список заказов, сумма без отменённых, число заказов по статусам |

## 3. Нефункциональные требования (U, R, P, S)

| № | Компонент | Требование |
|---:|---|---|
| U1 | Usability | Интерфейс на русском языке; создание заказа — не более 3 действий из главного меню; обучение оператора ≤ 30 минут |
| R1 | Reliability | Данные сохраняются на диск при штатном и аварийном завершении; резервное копирование ежедневно, восстановление ≤ 10 минут |
| R2 | Reliability | Невозможно создать заказ на количество больше остатка, в т. ч. при параллельной работе операторов |
| P1 | Performance | Формирование отчёта ≤ 2 с при базе до 10 000 заказов; создание заказа ≤ 1 с |
| P2 | Performance | Одновременная работа до 50 операторов без деградации отклика |
| S1 | Supportability | Модульная структура кода, соответствие PEP 8, покрытие тестами ≥ 70 % |
| S2 | Supportability | Статусы заказов и параметры магазина выносятся в файл настроек; операции с заказами логируются |

## 4. Ограничения («+»)

| № | Ограничение |
|---:|---|
| ОГР1 | Обработка персональных данных покупателей (ФИО, e-mail) — по ФЗ-152: минимум хранимых данных, разграничение доступа |
| ОГР2 | Реализация — Python 3.10+, стандартная библиотека (учебное ограничение проекта) |
| ОГР3 | Архитектура должна допускать замену хранения в памяти на СУБД без переписывания бизнес-логики |

## 5. Предположения

- П1. Предполагается, что складской учёт ведётся в одном магазине; многоскладская работа в версию 1.0 не входит.
- П2. Оплата заказов фиксируется вручную оператором (смена статуса); интеграция с платёжным шлюзом — за рамками версии 1.0.
- П3. Число товаров в каталоге не превышает 10 000 позиций; на больший объём требование P1 не распространяется.

## 6. Проверка соответствия стандартам

Документ проверен по модели FURPS+: все шесть компонентов заняты требованиями, «бесхозных» требований нет. По ISO/IEC/IEEE 29148 каждое требование проверено на однозначность и проверяемость: нефункциональные требования снабжены числовыми критериями приёмки. Покрытие по ГОСТ Р ИСО/МЭК 25010-2015: задействованы характеристики функциональная пригодность, удобство, надёжность, производительность, сопровождаемость.

## 7. Вывод

Составлен документ требований к системе управления заказами: 6 функциональных, 6 нефункциональных требований, 3 ограничения и 3 предположения. Явное выделение предположений (один склад, ручная фиксация оплаты) защищает проект от «расползания» границ, а числовые критерии делают каждое требование проверяемым при приёмке.
