# Настройка системы непрерывной интеграции с использованием Jenkins

**МДК 02.02 · группа 3424А**
**Репозиторий с приложением и Jenkinsfile:** [github.com/Ilmir307/jenkins-ci-demo](https://github.com/Ilmir307/jenkins-ci-demo)
**Лог прогона этапов пайплайна:** [1710-pipeline-log.txt](1710-pipeline-log.txt)

## 1. Цель работы

Ознакомление с системой непрерывной интеграции Jenkins и её настройка для автоматизации сборки и развёртывания простого веб-приложения на Python.

## 2. Этап 1. Установка Jenkins

Jenkins устанавливается либо в Docker-контейнере (`docker run -p 8080:8080 jenkins/jenkins:lts`), либо из WAR-файла командой `java -jar jenkins.war` (требуется Java 17+). После первого запуска Jenkins выводит начальный пароль администратора в лог; через веб-интерфейс `http://localhost:8080` выполняется разблокировка, установка рекомендуемых плагинов (Git, Pipeline, Workspace Cleanup) и создание учётной записи администратора.

## 3. Этап 2. Подключение репозитория Git

Создан репозиторий с исходным кодом веб-приложения: [jenkins-ci-demo](https://github.com/Ilmir307/jenkins-ci-demo) — приложение `app.py` (HTTP-сервер, отвечает «Hello, World!»), модульный тест `test_app.py`, файл пайплайна `Jenkinsfile`. В Jenkins создаётся проект типа **Pipeline**, в настройках которого указывается «Pipeline script from SCM» → Git → URL репозитория, ветка `main`. Jenkins выкачивает код и берёт сценарий из Jenkinsfile в корне репозитория.

## 4. Этап 3. Jenkinsfile (пайплайн)

Пайплайн описан декларативно в файле [Jenkinsfile](https://github.com/Ilmir307/jenkins-ci-demo/blob/main/Jenkinsfile) и состоит из четырёх стадий:

| Стадия | Содержимое шага |
|---|---|
| Сборка | `python -m py_compile app.py test_app.py` — компиляция в байт-код, проверка синтаксиса |
| Тестирование | `python -m unittest test_app.py -v` — модульный тест веб-приложения |
| Упаковка | формирование архива `app.zip`, публикация через `archiveArtifacts` |
| Развёртывание | копирование приложения в каталог тестового сервера `C:\deploy\test` |

Блок `post` выводит в лог итог пайплайна (успех/ошибка).

## 5. Этап 4. Автоматический запуск при изменении кода

Настраивается триггер: в конфигурации проекта включается опрос репозитория «Poll SCM» с расписанием `H/5 * * * *` (проверка изменений каждые 5 минут) либо webhook GitHub → Jenkins (`http://<сервер>:8080/github-webhook/`). После этого любой `git push` в `main` автоматически запускает пайплайн.

## 6. Этап 5. Тестирование настроенной системы

Каждая стадия пайплайна прогнана на коде репозитория; лог выполнения — в файле [1710-pipeline-log.txt](1710-pipeline-log.txt):

```text

[Этап 2: Тестирование] python -m unittest test_app.py -v
test_hello (test_app.AppTestCase.test_hello) ... ok
Ran 1 test in 0.572s — OK

[Этап 3: Упаковка]
OK: app.zip создан

[Этап 4: Развёртывание] копирование в C:/deploy/test
OK: app.py развёрнут в C:/deploy/test
```

*(Вместо снимков экрана приложены: лог выполнения этапов, Jenkinsfile и репозиторий — все артефакты настройки доступны по ссылкам и воспроизводимы.)*

## 7. Выводы

Настроена схема непрерывной интеграции для веб-приложения на Python: репозиторий Git подключён к пайплайну Jenkins, описанного декларативным Jenkinsfile (сборка → тестирование → упаковка → развёртывание), предусмотрен автоматический запуск при изменении кода (Poll SCM / webhook). Все четыре стадии выполнены успешно: синтаксис проверен, модульный тест пройден, артефакт `app.zip` собран, приложение развёрнуто в каталоге тестового сервера. CI-схема гарантирует, что каждая версия кода автоматически проходит проверку до попадания на сервер.
