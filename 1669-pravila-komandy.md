# Правила взаимодействия в команде разработчиков

**Проект: создание информационной системы · МДК 02.02 · группа 3424А**
**Презентация:** [1669-pravila-komandy.pptx](1669-pravila-komandy.pptx)

## 1. Цель документа

Разработать правила взаимодействия в команде разработчиков, обеспечивающие эффективную работу и достижение целей проекта по созданию информационной системы.

## 2. Выбор методов организации работы

Рассмотрены три метода: **Waterfall** (последовательные этапы, жёсткий план), **Scrum** (спринты с регулярной поставкой результата) и **Kanban** (непрерывный поток задач с WIP-лимитами).

Для проекта выбран **Scrum с элементами Kanban (Scrumban)**. Обоснование: требования заказчика к информационной системе будут уточняться, поэтому нужны короткие итерации и демо (Scrum); при этом часть задач (исправление ошибок, мелкие доработки) поступает непрерывно и плохо укладывается в спринты — их обслуживает доска Kanban с лимитами на незавершённую работу.

## 3. Правила взаимодействия

### 3.1. Распределение обязанностей

| № | Правило |
|---:|---|
| 1.1 | У каждой задачи есть один ответственный исполнитель; совместная задача делится до атомарных |
| 1.2 | Product Owner единолично управляет приоритетами бэклога; команда не берёт задачи «со стороны» |
| 1.3 | Ведущий разработчик отвечает за архитектуру и код-ревью; решения фиксируются в wiki |

### 3.2. Коммуникация

| № | Правило |
|---:|---|
| 2.1 | Ежедневный стендап — 15 минут: что сделано, что делаю, что мешает |
| 2.2 | Рабочие вопросы — в общем чате, а не в личке: ответ виден всей команде |
| 2.3 | Блокирующая проблема озвучивается сразу, а не на следующей встрече |
| 2.4 | Все договорённости из устных обсуждений фиксируются текстом в задаче или wiki |

### 3.3. Управление версиями и кодом

| № | Правило |
|---:|---|
| 3.1 | Основная ветка `main` защищена: прямые коммиты запрещены, только pull request |
| 3.2 | На каждую задачу создаётся отдельная ветка `feature/<номер>-<тема>` |
| 3.3 | Слияние — только после код-ревью и зелёных автотестов |
| 3.4 | Сообщения коммитов пишутся осмысленно: что и зачем изменено |
| 3.5 | Код соответствует PEP 8; проверка линтером обязательна перед PR |

### 3.4. Работа с задачами

| № | Правило |
|---:|---|
| 4.1 | Статусы на доске обновляются ежедневно: «запланировано → в работе → на проверке → готово» |
| 4.2 | Задача «готова», только если она протестирована и прошла ревью (Definition of Done) |
| 4.3 | В работе одновременно — не более 2 задач на человека (WIP-лимит) |

## 4. Отслеживание и корректировка правил

- **Ретроспектива раз в 2 недели:** команда обсуждает, какие правила работают, а какие мешают; решение об изменении фиксируется в этом документе.
- **Метрики процесса:** время задачи в работе, число возвратов с ревью, число просроченных задач — рост метрики сигналит, что правило не выполняется или устарело.
- **Владелец документа:** Scrum Master следит за соблюдением правил и вносит согласованные изменения; версия документа хранится в Git вместе с кодом.

## 5. Вывод

Разработаны правила взаимодействия команды по четырём направлениям: обязанности, коммуникация, управление версиями, работа с задачами. Правила опираются на выбранный метод Scrumban и охватывают полный цикл задачи — от бэклога до слияния в `main`. Механизм корректировки (ретроспективы, метрики, владелец документа) делает правила живым инструментом, а не формальностью: команда регулярно пересматривает их по факту работы.
